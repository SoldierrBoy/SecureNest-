# SecureNest — Лабораторна робота №6

**Дисципліна:** Безпека програм та даних  
**Тема:** Розробка безпечної системи управління обліковими записами  
**Платформа:** ASP.NET Core MVC 10 / C# / EF Core / SQLite / ASP.NET Core Identity  
**Мова інтерфейсу:** українська

## Коротке вступне слово та стек технологій

У цій лабораторній роботі я розробив **SecureNest** — вебзастосунок для безпечного керування обліковими записами користувачів. У ньому можна реєструватися, входити до системи, підтверджувати електронну пошту, увімкнути двофакторну автентифікацію, відновлювати пароль та входити через Google. Також реалізовано захист від підбору паролів і розмежування доступу між користувачем та адміністратором.

Для реалізації проєкту я використав такі технології:

- **C# та .NET 10 / ASP.NET Core MVC** — серверна частина, маршрути й логіка вебзастосунку.
- **ASP.NET Core Identity** — реєстрація, автентифікація, безпечне хешування паролів (PBKDF2), ролі `User` і `Admin`, блокування після невдалих входів та 2FA через TOTP.
- **Entity Framework Core та SQLite** — робота з базою даних, зберігання користувачів і журналу входів.
- **Razor Views, HTML, CSS і JavaScript** — сторінки сайту та адаптивний інтерфейс.
- **Google OpenID Connect** — вхід через зовнішній Google-акаунт.
- **Email-токени та локальна тестова пошта / SMTP** — активація облікового запису та відновлення пароля.
- **HTTPS, CAPTCHA, аудит подій і RBAC** — додаткові механізми захисту.

Застосунок побудовано за архітектурою **MVC (Model–View–Controller)**: контролери обробляють запити, сервіси виконують окремі функції безпеки, а дані зберігаються в SQLite. Проєкт розроблено для локальної демонстрації вимог лабораторної роботи №6.

## 1. Швидкий запуск на Windows 11

Потрібні **.NET 10 SDK**, браузер та інтернет тільки під час першого завантаження NuGet-пакетів. Сама система (без Google та справжнього SMTP) працює локально без зовнішніх сервісів.

1. Завантажте SDK із https://dotnet.microsoft.com/download/dotnet/10.0 (саме **SDK**, не тільки Runtime).
2. Розпакуйте проєкт у папку без архіву. Відкрийте цю папку в PowerShell.
3. Виконайте команди:

   ```powershell
   dotnet --version
   dotnet dev-certs https --trust
   dotnet restore
   dotnet run --launch-profile SecureAccountsLab6
   ```

   Або двічі натисніть `scripts/Run-Lab.ps1` з PowerShell (приклад нижче). Інтернет при першому `dotnet restore` потрібен для NuGet.
4. Відкрийте **https://localhost:7080** у браузері. Для Google OpenID Connect використовуйте саме HTTPS.
5. **При першому запуску** у консолі з'явиться випадково згенерований пароль адміністратора:

   ```text
   LOCAL DEMO ADMIN — SAVE THESE CREDENTIALS:
   EMAIL:    admin@lab.local
   PASSWORD: <випадковий секрет, ваш буде іншим>
   ```

   Збережіть його. Пароль адміністратора **не зашитий у проєкт** і зберігається в БД як хеш.
6. Нові листи активації/відновлення відкривайте в **https://localhost:7080/dev/mail**.

> **Важливо:** при наступних запусках пароль адміністратора вже не друкується: він зберігається в БД у вигляді хешу. Якщо загубили пароль локального демо-адміна, закрийте застосунок та запустіть:  
> `dotnet run --launch-profile SecureAccountsLab6 -- --reset-demo-admin`  
> Цей режим працює **лише в Development**; новий пароль виведеться в консоль.

### Що робити, якщо PowerShell не дозволяє запустити .ps1

Просто виконайте чотири команди вище вручну. Змінювати політику виконання PowerShell для цього не потрібно.

## 2. Як виконати всі 7 завдань

| Завдання з методички | Реалізація / де показувати |
|---|---|
| 1. Реєстрація, складність пароля, вхід/вихід | `/auth/register` → `/auth/login` → `/profile`; Identity PasswordHasher (PBKDF2); перевірка 8+ / великі + малі / цифри / символи |
| 2. CAPTCHA під час реєстрації | SVG CAPTCHA із 6 випадковими символами, 4-хвилинним строком і одноразовою перевіркою |
| 3. Активація email | Після реєстрації `/dev/mail` → лист `ACTIVATION` → відкрити посилання → email підтверджений |
| 4. Brute Force, журнал та блокування | 5 помилок → 15 хвилин Identity Lockout; `/admin/logs`; `/admin` блокування/розблокування |
| 5. 2FA (TOTP) | Профіль → Безпека → додати ключ до Google/Microsoft Authenticator → підтвердити код → вийти/увійти з 2FA |
| 6. OpenID Connect | Вхід через Google із Authorization Code + PKCE, **потребує власних Google ClientId/ClientSecret** (інструкція нижче) |
| 7. Відновлення пароля | `/auth/forgot-password` → лист `RESET` у `/dev/mail` → новий пароль; токен дійсний одну годину |

**Додаткові вимоги:** дві ролі `User`/`Admin`; обмеження доступу через `[Authorize]` та `[Authorize(Roles="Admin")]`; користувач бачить тільки власний профіль; адміністратор бачить email, статус активації, ручне блокування, кількість помилкових входів, повний журнал подій із IP/часом/результатом.

## 3. Як увімкнути справжній вхід через Google

Без особистого **Client ID та Client Secret** від Google жоден проєкт не може виконати справжній OIDC-вхід; у цій збірці всі серверні маршрути й логіка готові, але кнопку приховано до налаштування.

1. Перейдіть до **Google Cloud Console**: https://console.cloud.google.com/ . Створіть або виберіть проєкт.
2. Налаштуйте Google Auth Platform: Branding, Audience та Data Access (`openid`, `email`, `profile`). Для режиму Testing додайте свій Google-акаунт до тестових користувачів.
3. Створіть OAuth Client типу **Web application**.
4. Вкажіть авторизовану адресу перенаправлення **`https://localhost:7080/signin-google`**. За потреби додайте origin **`https://localhost:7080`**.
5. У PowerShell у корені проєкту виконайте (замість тексту в лапках — власні значення):

   ```powershell
   dotnet user-secrets set "Authentication:Google:ClientId" "ВАШ_CLIENT_ID"
   dotnet user-secrets set "Authentication:Google:ClientSecret" "ВАШ_CLIENT_SECRET"
   dotnet run --launch-profile SecureAccountsLab6
   ```

6. На сторінці входу з'явиться **«Увійти через Google»**. Натисніть → пройдіть вхід Google → перевірте свій профіль.

**Примітка щодо безпеки:** система приймає тільки підтверджений Google email. Якщо адреса вже зареєстрована локально, вона **не прив'язується автоматично** (захист від захоплення акаунта). Спочатку ввійдіть локальним паролем та натисніть **«Прив'язати Google»** у своєму профілі.

Якщо Google показує `redirect_uri_mismatch`, скопіюйте точну адресу `https://localhost:7080/signin-google` в налаштуваннях OAuth клієнта (без кінцевого `/`). Якщо браузер не довіряє локальному сертифікату, повторіть `dotnet dev-certs https --trust`.

## 4. Як налаштувати справжню електронну пошту SMTP

Локальний режим створений спеціально для відеозахисту: листи надходять у вебінтерфейс **`/dev/mail`**, доступний лише у Development і тільки з loopback-адреси. Для відправлення реальних листів перемкніть `Mail:Mode` у `Smtp` та налаштуйте SMTP.

Надійніше записати параметри через **user-secrets**, не класти паролі до Git:

```powershell
dotnet user-secrets set "Mail:Mode" "Smtp"
dotnet user-secrets set "Mail:From" "SecureNest <your-address@example.com>"
dotnet user-secrets set "Mail:Smtp:Host" "smtp.example.com"
dotnet user-secrets set "Mail:Smtp:Port" "587"
dotnet user-secrets set "Mail:Smtp:Username" "your-address@example.com"
dotnet user-secrets set "Mail:Smtp:Password" "YOUR_SMTP_APP_PASSWORD"
dotnet user-secrets set "Mail:Smtp:EnableSsl" "true"
```

Провайдер пошти повинен підтримувати SMTP/STARTTLS, із дозволеним входом через пароль застосунку або спеціальні SMTP-облікові дані. `SmtpClient` застосовано для навчального проєкту. Для серйозного продакшну рекомендований сучасний email-сервіс із чергою доставки й моніторингом.

> Після вибору SMTP листи більше не з'являтимуться у локальному поштовому ящику; вони надсилатимуться фактично на адреси користувачів.

## 5. Архітектура

```text
Браузер (Razor Views + CSS + JavaScript)
            |
       HTTPS / MVC
            |
  ASP.NET Core Controllers
  ├── AuthController       — реєстрація, вхід, MFA, активація, Google, відновлення
  ├── ProfileController    — персональний кабінет, керування 2FA, прив'язка Google
  ├── AdminController      — RBAC, користувачі, блокування, журнал
  ├── CaptchaController    — одноразова SVG CAPTCHA
  └── DevMailController    — тестова пошта (лише localhost + Development)
            |
        Services
  ├── CaptchaService      — криптографічна випадковість + одноразовий SHA-256
  ├── AuditService        — журнал подій (без паролів і секретів)
  └── AppMailer           — dev-outbox / справжній SMTP
            |
       ASP.NET Identity
  ├── PBKDF2 PasswordHasher / Lockout
  ├── Data Protection Token Providers
  ├── TOTP Authenticator Provider
  └── Google OpenID Connect (Authorization Code + PKCE)
            |
      EF Core + SQLite
  ├── AspNetUsers, AspNetRoles, AspNetUserRoles, ...
  ├── LoginAudits
  └── DevMails (тільки демонстрація)
```

- **Models** — `AppUser`, `LoginAudit`, `DevMail`.
- **ViewModels** — вхідні дані форм та адміністративна статистика.
- **Data** — контекст EF Core та початкове налаштування ролей/адміністратора.
- **Services** — окрема логіка CAPTCHA, аудиту, пошти.
- **Controllers** — обробники HTTP-запитів, авторизація та сценарії користувача.
- **Views** — Razor HTML-шаблони.
- **wwwroot** — адаптивний стиль та прості скрипти інтерфейсу.

## 6. Основні механізми захисту

- **Паролі**: пароль не зберігається відкритим текстом. Identity генерує для кожного пароля сіль та зберігає результат PBKDF2 в стандартному Identity-форматі, перевіряючи введений пароль алгоритмом верифікації.
- **Політика**: від 8 символів, велика і мала літери, цифра, спеціальний символ, мінімум 4 різних символи.
- **Cookies**: HttpOnly, SameSite=Lax; Secure в HTTPS Production; Data Protection key ring зберігається в `App_Data/keys`.
- **CSRF**: автоматична перевірка AntiForgeryToken для MVC POST-форм.
- **Brute Force**: вбудована блокування на 15 хв після 5 помилок, плюс IP rate limiting. Кожен вхід записується в журнал; невдала TOTP-перевірка теж логуються.
- **CAPTCHA**: 6 криптографічно випадкових символів, PNG не потрібен — SVG; session збережена на сервері, відповідь зберігається як SHA-256, 4-хвилинний TTL, споживання після першої спроби. Це достатній **навчальний механізм**, але не замінює промислову CAPTCHA з оцінкою ризику.
- **Активація та відновлення**: токен Identity Data Protection, термін 60 хвилин; підтвердження email після першого успішного використання вже не повторюється, а reset-token анулюється після зміни пароля/security stamp.
- **2FA**: TOTP (RFC 6238-подібний стандарт), код змінюється приблизно кожні 30 секунд, можна увімкнути/вимкнути зі своїм чинним TOTP-кодом; секретний ключ не публікується стороннім.
- **RBAC**: роль `Admin` необхідна для `/admin` та `/admin/logs`. Сам себе або іншого адміністратора вручну заблокувати не можна. При блокуванні оновлюється security stamp, активні cookie-сесії втрачають чинність.
- **Google OIDC**: authorization code, PKCE, кореляційний state, перевірка підтвердженого email, без автоматичного злиття локальних акаунтів.
- **Захисні заголовки**: CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy.

## 8. Примітки та обмеження

1. Проєкт задумано для **локальної навчальної демонстрації**. У ньому використано `EnsureCreatedAsync()` для автоматичного створення SQLite. Для реального розгортання потрібні окремі EF Core migrations, захищена та резервована база й контроль секретів.
2. Для реального Google-входу необхідні зовнішні Google OAuth-облікові дані; **ці секрети неможливо законно або безпечно додати універсальними значеннями в архів**.
3. Локальний dev-outbox **не означає відправку листа на справжню пошту**. 
4. Локальна CAPTCHA не має антибот-сигналів, як Cloudflare Turnstile / hCaptcha, тому для публічного продакшну її слід замінити.
5. У прикладі **не виконана реальна перевірка компіляції в середовищі підготовки архіву**, оскільки там відсутній .NET SDK. Після встановлення SDK обов'язково виконайте `dotnet restore` та `dotnet build` перед відеозаписом.

Це вебзастосунок із готовою логікою семи завдань, а не production-certified система для реальних користувачів.
